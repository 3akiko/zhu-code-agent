# A. 项目全局

## A1. 为什么做这个项目？动机是什么？
**考察点**：判断你是"为了简历"还是"真懂 agent 机制"；有没有自己的思考。
**参考答案**：
- 三条动机：① 学习 agent 核心机制——流式对话、工具调用、权限控制、上下文管理，这些是 LLM 应用的主干；② 为 agent 开发面试准备一个"架构 + 代码 + 文档 + 测试 + 对比"都完整的项目；③ 对标 Claude Code / Codex，验证"用 Java 从零能不能搭出一个可用的命令行 coding agent"。
- 选 Java 而非 Python/TS：想证明工程能力（Java 21 虚拟线程/结构化并发、强类型、Maven 生态），也避开"大家都用 Python 套 LangChain"的路径，展示自己能从协议层手写。
- 关键取舍：不抄 LangChain 之类框架，`LlmClient`/`StreamEvent`/`ToolExecutor` 都是自研抽象——为了讲清楚"每一层为什么这么设计"。

## A2. 整体架构怎么分层？画一下数据流。
**考察点**：能否清晰讲出模块边界与依赖方向（架构题必考）。
**参考答案**：
- 分层（自上而下、无环依赖）：
  - `tui/`（ChatApp 状态机 + JLine3 + SlashCommands + TurnInterruptController）→ 只负责交互与展示
  - `agent/AgentRunner` → ReAct 消息循环（消费 StreamEvent、驱动工具、汇总 Result）
  - `llm/`（LlmClient 接口 + Anthropic/OpenAI 实现 + SseParser + LlmStream）→ 协议无关的流式事件
  - `tool/` + `permission/` → 工具执行与权限判定（ToolExecutor 接口，串行/并行只换实现）
  - `conversation/`、`session/`、`context/` → 历史/落盘/压缩
- 一次用户输入的数据流：ChatApp `sendAndRender` → AgentRunner 循环 → `LlmClient.stream()` 后台线程拉 SSE → SseParser 逐事件解析 → 写入 `LlmStream` 队列 → 循环消费：文本增量直接渲染、`ToolCall` 交给 SerialToolExecutor（权限确认 → 执行 → tool_result 一次性回填）→ 直到 `end_turn` → 汇总 Result → ChatApp 展示完成行 + 落盘。
- 关键点：**协议差异被密封在 llm/ 层**（StreamEvent 统一事件），上层（循环/会话/UI）完全不知道是 Anthropic 还是 OpenAI。

## A3. 项目最大的技术亮点是什么？（追问：最有挑战/踩坑最深的一个）
**考察点**：你对自己的代码有没有"亮点意识"；踩坑能讲多深。
**参考答案**（选 2-3 个展开）：
- **协议无关的双后端抽象**：`StreamEvent` 密封接口把 anthropic `tool_use` / openai `function_call`、thinking 差异全部收敛成 6 种事件，调用方零感知；加协议 = 加一个客户端类 + 工厂分支。
- **上下文管理的"协议感知占用"**：真机发现 DeepSeek `/anthropic` 端点的 `input_tokens` **不含缓存命中**（`cache_read_input_tokens` 单独返回），而 OpenAI `prompt_tokens` 含缓存——于是占用率按协议区分（Anthropic = input+cacheRead，OpenAI = prompt_tokens），否则告警/自动压缩在 Anthropic 协议上永不触发。这个发现来自真机对比样例（OpenAI 第 2 轮 723=640+83，Anthropic 第 2 轮 42+768）。
- **Ctrl+C 流式中断的演进**：受限 PTY（DumbTerminal）下 JLine 不注册信号 → 改用 JVM 级 `Signals.register`；Apple Silicon 弱内存模型下信号线程写/主线程读不可见 → volatile + AtomicBoolean；二次 Ctrl+C 逃生门（对齐 Codex「再按一次退出」）。一个功能踩了三层坑。
- **分层渐进压缩**：先零成本本地瘦身（丢低价值 tool 对、截断超长结果），再 LLM 摘要折叠（最旧 N 轮），不引入本地 tokenizer（占用全以 API usage 复核）。

## A4. 和 Claude Code / Codex 比，你的取舍是什么？
**考察点**：对比意识 + 诚实（知道差距在哪）。
**参考答案**：
- 做到同级的：双协议接入、ReAct 工具循环、权限三档（normal/acceptEdits/bypass）、/plan 先计划后执行、快照 undo/rewind、prompt 缓存、Ctrl+C 中断。
- 差在哪（诚实说）：Claude Code 压缩是四层（snip → microcompact → context collapse → auto-compact，含 cache-aware 决策），我是两层；Claude Code/Codex 有 OS 级沙箱（Seatbelt/Landlock），我目前是应用层守卫（M7 规划）；Codex 有 MCP/subagents/hooks（我 M5/M6 规划）；Codex 有非交互 `-p`（我 M8+）。
- 为什么这样取舍：渐进式——先把单 agent 闭环做到可靠，再上并行/生态；面试讲"我知道差距、有明确 roadmap、且每步都有验收"反而是加分项。

## A5. 项目规模？
**考察点**：工程量感知。
**参考答案**：~80 个源文件（main+test），M1–M4 四个里程碑，215 个 JUnit 测试全绿（mock HTTP + 脚本化 LLM 端到端，不依赖真实密钥）；真机 DeepSeek 冒烟过 M2/M3/M4 demo；文档体系完整（spec/plan/task/checklist 四文档 + 验收报告 + 实现记录 + 对比表）。

# B. 协议抽象与流式

## B1. `StreamEvent` 为什么设计成 sealed interface？事件有哪些？
**考察点**：Java 17+ sealed 语法 + 事件驱动设计。
**参考答案**：
- sealed 让"事件全集"编译期封闭：`TextDelta` / `ThinkingDelta` / `ThinkingComplete` / `ToolCall` / `StreamEnd` / `Error`，新增事件必须显式改父接口——**穷举匹配不会漏**（switch 可穷举），这是协议收敛的骨架。
- 语义：文本增量、思考增量（灰字实时滚动）、思考结束携带 signature（Anthropic 多轮回传必需）、工具调用声明（M2 加入）、流结束（stop_reason + in/out + cache 命中）、错误（脱敏消息）。
- `StreamEnd` 是"正常结束必达"的最后事件；出错只发 `Error`——消费方按这个契约写就不会漏。

## B2. 怎么把 anthropic `tool_use` 和 openai `function_call` 收敛成统一的？
**考察点**：协议归一化的具体做法。
**参考答案**：
- 请求侧：两个客户端各自把统一 `ToolSpec` 翻译成协议原样——Anthropic 用顶层 `tools` 数组（name/description/input_schema + cache_control），OpenAI 用 `tools:[{type:function,function:{name,description,parameters}}]`。
- 响应侧：Anthropic 在 `content_block_start(tool_use)` + `input_json_delta` 累积参数，`content_block_stop` 时发 `ToolCall(id,name,argumentsJson)`；OpenAI 按 `delta.tool_calls[index]` 累积（id/name/arguments 分片），流结束前按 index 排序一次性发出——两端收敛成同一个 `ToolCall`。
- 回填侧：`tool_result` 按协议回传（Anthropic 内嵌 user 消息块 / OpenAI `role=tool` 消息），上层只操作统一 `ContentBlock`。
- 收益：AgentRunner / 会话 / UI 不感知协议；新增协议零改动调用方（工厂 + 一个客户端类）。

## B3. SSE 流式怎么解析？遇到断流/异常怎么办？
**考察点**：流式协议细节 + 容错。
**参考答案**：
- `SseParser`：按行喂入，`event:`/`data:` 字段行累积，空行触发一个完整事件；多行 data 以 `\n` 连接（Anthropic 的 thinking/参数分片就是多行 data）；Anthropic 按 `event:` 类型（message_start/content_block_*/message_delta/message_stop/ping）分发，OpenAI 按 `data:` 的 JSON 结构 + `[DONE]` 结束。
- 容错：解析异常 → 发 `Error` 事件（消息脱敏，不含 api_key）；HTTP 层失败同样转 `Error`。
- 超时防护：每步"流空闲超时 120s"——该步开始后连续无事件就中断（宽容长思考，但防挂死）；bash 工具另有 30s 超时。
- 中断：`LlmStream.cancel()` 取消在途请求 + `join()` 等流线程结束，保证退出/中断不泄漏线程。

## B4. extended thinking 怎么展示和多轮回传？
**考察点**：一个"看起来简单、实际有协议坑"的点。
**参考答案**：
- 展示：`ThinkingDelta` 事件 → TUI 灰色小字实时滚动；`ThinkingComplete(signature)` 后正文正常颜色。
- 回传（关键坑）：Anthropic 要求后续请求必须带**上一轮的 thinking 块 + signature**，否则报错；所以 assistant 消息里 `thinking` 和 `thinkingSignature` 要随会话一起落盘/回传（会话 JSON 契约的一部分）。
- OpenAI 侧（deepseek-reasoner）：思考在 `delta.reasoning_content`，展示灰字，统计在 `completion_tokens_details.reasoning_tokens`，不要求回传 signature——两端语义不同，同样由客户端收敛。

## B5. 为什么 M4 引入 `LlmStream`（队列 + cancel/join）？
**考察点**：异步/线程模型演进。
**参考答案**：
- 之前 `stream()` 直接返回事件队列；M4 为了支持**流式中断**和**优雅关闭**，包装成 `LlmStream`：内部 `BlockingQueue` + `cancel()`（中断 HTTP 流）+ `join()`（等后台线程结束）。
- 好处：中断路径统一——退出时对在途流 cancel + join（带超时），不再"JVM 退出直接掐 daemon 线程"；也为 M5 并行流（多个 LlmStream 同时跑）提供了 per-call 句柄。

## B6. 新增一个后端/协议，要改哪些地方？
**考察点**：抽象是否真的"开放扩展、封闭修改"。
**参考答案**：一个实现类（继承 `AbstractStreamingClient`，实现 buildRequest / handleEvent / isStreamEnd）+ `LlmClientFactory` 加一个分支 + 配置里加 provider。调用方（AgentRunner/会话/UI/压缩器）零改动。这是本项目"协议无关"承诺的验证方式，也常用于反问"你凭什么说新增协议零改动"。

# C. Agent 循环与工具

## C1. 你的 ReAct 循环是怎么实现的？
**考察点**：能不能讲清"循环 + 终止条件 + 状态机"。
**参考答案**：
- `AgentRunner.runLoop`：addUser（首轮）→ 循环 `consumeStep`：
  - 发请求（systemPrompt + 历史 + tools）→ 消费流事件：文本/思考直接回显；`ToolCall` 记录；
  - 步骤结束（StreamEnd）按 stop_reason 分支：`tool_use` → 执行工具 → tool_result 回填 → 继续下一轮；`end_turn` → 结束；
- 终止与护栏：单轮工具调用上限 60（防失控循环，到了提示"输入『继续』开新一轮"）+ 每步流空闲超时 120s。
- 一次"推理 → 工具调用 → 执行 → 回填 → 再推理"就是 ReAct 的 think/act/observe，只是观察源从环境换成工具结果。

## C2. tool_result 为什么必须"一次性回填"？同一消息多个工具怎么处理？
**考察点**：协议硬性约束（Anthropic 明确要求）。
**参考答案**：
- Anthropic 协议要求：同一条 assistant 消息里的所有 tool_use，必须由紧接着的**一条** user 消息一次性回填全部 tool_result，不能拆散、不能穿插别的。
- 实现：同一轮里多个 ToolCall 先全部收集（串行执行，按 index 保序），然后一次性构造回填消息（Anthropic 一个 user 消息多个 tool_result 块 / OpenAI 多条 role=tool 消息）。
- 这也是 M5 并行工具执行的约束来源：并行执行没问题，但**回填顺序必须按原调用顺序**（保序），否则协议层就乱了。

## C3. 模型调用不存在的工具 / 参数不合法怎么办？
**考察点**：鲁棒性 + 容错回填。
**参考答案**：
- 目前：工具名/参数解析失败或执行失败 → 返回**可读错误**的 tool_result 回填（如 `edit_file` 要求唯一匹配，未找到/多匹配返回具体错误），模型看到后自行调整重试——这就是"让模型自愈"的闭环。
- 计划中（M8+）：按 `ToolSpec.inputSchema` 做**结构化参数校验 + 失败重试回填**，减少模型"瞎猜参数"的轮次浪费（roadmap 已记录）。
- 单轮 60 步上限兜底：即使模型反复出错也不会无限循环。

## C4. 工具结果太大怎么办？（bash 输出 / tool_result 落盘）
**考察点**：资源上限意识。
**参考答案**：双截断——bash 输出上限 200KB（超了截断标注）；tool_result 落盘单条 64KB（内存完整、落盘截断标注，压缩时可再截断）；UI 预览行数 `ui.tool_preview_lines` 可配（默认 5 行，超出折叠「…已截断」）。三层视角：内存可全量、展示可预览、落盘可截断，各有上限不互相拖累。

## C5. 一轮为什么上限 60 步？空闲超时为什么 120s？
**考察点**：护栏设计的取舍。
**参考答案**：60 步是"够用但防失控"的经验值（正常任务几步到十几步）；触发后不崩溃，提示可继续（把控制权交还用户）。120s 空闲超时针对"长思考"：流式下思考期间可能长时间无事件，太短会误杀，太长会挂死，120s 是实测折中；它按"该步开始后连续无事件"计，不是总时长。

# D. 安全体系

## D1. 三层安全体系具体是什么？为什么分层？
**考察点**：纵深防御思路（面试高频）。
**参考答案**：路径边界（PathGuard）→ 命令/参数守卫（DangerGuard）→ 交互权限（PermissionManager 三档）。分层理由：**单点失效兜底**——权限模式只决定"要不要问"，不决定"能不能做"；即使 bypass 模式下，危险命令/越界路径仍被下两层硬拒（红线不削弱）。

## D2. PathGuard 怎么防路径穿越和符号链接？
**考察点**：真实安全细节。
**参考答案**：
- 工作区为根：所有文件工具的目标必须 resolve 到 cwd 之内；
- **realpath 统一比较**（处理 macOS `/var ↔ /private/var` 这类别名）；
- 符号链接校验：候选路径 realpath 后必须仍在工作区，防止 `cwd/ok -> /etc` 这类链；
- 禁写 `.git/` 与程序自身目录（`~/.zhu-code-agent/`）。

## D3. DangerGuard 危险命令怎么判断？为什么 rm -rf 即使"总是允许"也强制确认？
**考察点**：安全设计 + 反绕过。
**参考答案**：
- 目标限工作区：**所有文件系统修改命令（rm/rmdir/mv/cp）的目标必须位于工作区内，与 flags 无关**——防 `rm -rf $HOME`、`cp x /etc`；
- shell 展开字符拒绝：目标含 `~ $ 反引号 $( ) ; & | < >` 直接拒绝（防 `rm -rf ~/x`、`$HOME/x` 展开绕过静态校验）；
- 危险命令（rm -rf 等）即使曾「总是允许」也强制确认——因为"总是允许"是内存级快捷授权，不代表用户授权了破坏性操作；红线交给规则而非用户记忆。

## D4. 权限三档模式怎么设计？
**考察点**：交互效率 vs 安全的平衡。
**参考答案**：normal（写类/bash 每步行内确认 a/d/s）/ acceptEdits（写文件自动批准，bash 仍确认）/ bypassPermissions（bash 非危险也自动批准）；只读工具一律自动放行。「总是允许」按工具+关键参数记忆（文件写按路径、bash 按完整命令串），仅内存、退出重置、不落盘。M5 子任务规划里每个子任务要有独立权限上下文与护栏上限。

## D5. api_key 怎么保证不泄漏？
**考察点**：安全意识。
**参考答案**：四级——① 配置支持 `${ENV_VAR}` 引用，不写明文；② `ProviderConfig.toString()` 刻意不打印 key；③ 会话 JSONL / 错误消息脱敏（错误事件先脱敏再上抛）；④ 快照/摘要请求不携带密钥。有专门的测试断言「会话文件不含 api_key」。

## D6. 用户让模型写 `~/.ssh` 或 `/etc` 会怎样？
**考察点**：把抽象落到具体场景。
**参考答案**：PathGuard 兜底拒绝（工作区外）；若是破坏性 bash 命令，DangerGuard 再拦一层（目标越界 / 危险命令强制确认）；只有工作区内、且用户显式允许（a/s）才执行。面试可补一句"我理解这里要的是纵深防御，不是单靠某一个开关"。

# E. 文件编辑 / /plan / 回滚

## E1. diff 为什么不引库、自己写？
**考察点**：工程取舍（依赖 vs 可控）。
**参考答案**：需求是"展示 change"而非"完整 diff 合并"，用公共前缀/后缀 + 中间变更块就够了（零依赖、几十行）；超长截断（`ui.diff_max_lines` 默认 200）只做展示、不影响落盘。真要复杂场景（大文件对比、三路合并）再引库也不迟——面试讲"先最小实现解决 80% 场景，明确知道升级路径"。

## E2. `/plan` 怎么保证零副作用？
**考察点**：约束传播。
**参考答案**：`PlanModeExecutor` 是只读执行器——write/edit/bash 在计划阶段被拦截并回填"该操作被计划模式禁止"；计划完成 = 模型 end_turn（最终文本即计划）；审批 `y` 才切到正常执行器（写仍按权限模式确认）；`d` 拒绝、任意文本作为修改意见重新生成。实现上是"同一 runLoop + 不同 executor/systemPrompt"，没有独立的模式状态机，状态少、不易错。

## E3. undo/rewind 为什么用全量快照而不是补丁？
**考察点**：设计取舍。
**参考答案**：全量快照回滚 = 直接写回，不依赖 diff 正确性、天然幂等；跨会话持久化（`~/.zhu-code-agent/snapshots/<会话ID>/checkpoints.json`）让"重开还能反悔"。代价是空间（>10MB 文件跳过快照、注明"不可回滚"），但编码工具场景文件通常小，全量更稳。快照在写前取、成功保留、失败丢弃。

## E4. 回滚会覆盖用户后来的手动修改吗？怎么处理？
**考察点**：诚实 + 已知边界。
**参考答案**：当前 undo/rewind 直接恢复检查点内容，**不检测**"回滚前文件又被改过"——这是已知边界（TODO 已记，规划 M7 与 git 集成时做"恢复前比对当前内容与检查点后一状态，不一致则提示"）。面试主动讲已知边界比被问到才承认要好。

# F. 上下文管理与稳定性

## F1. 上下文占用率怎么算？为什么"协议感知"？
**考察点**：真机踩坑 + 对 API 语义的理解。
**参考答案**：
- 占用 = 最近一次请求真实输入 / context_window。但两个协议语义不同：
  - OpenAI：`prompt_tokens` 官方定义 = 缓存命中 + 未命中，**已含缓存**，直接用；
  - Anthropic（含 DeepSeek `/anthropic`、真实 Claude）：`input_tokens` **只含未缓存部分**，`cache_read_input_tokens` 单独返回，占用 = input + cacheRead。
- 真机证据（`docs/DeepSeek-OpenAI-vs-Anthropic/`）：同前缀第 2 轮，OpenAI `prompt_tokens=723（=640 hit + 83 miss）`，Anthropic `input=42 + cacheRead=768 = 810`。如果只用 input_tokens，Anthropic 协议上告警/自动压缩**永远不会触发**（810 显示成 42）。实现：`ProviderConfig.occupancyBasis(input, cacheRead)` 按协议归一，一次真机对比就把问题暴露了。

## F2. 自动压缩怎么做？为什么"先本地瘦身、再 LLM 摘要"？
**考察点**：成本/效果分层。
**参考答案**：两层渐进——
1. **零成本本地瘦身（snip）**：丢弃"空结果 / 已拒绝执行 / 权限禁止"的低价值 tool 配对（整对丢，不破坏交替）；截断 >64KB 的 tool_result；
2. **LLM 摘要折叠**：最旧 N 轮折叠成一条带「【上下文已压缩】」标记的 user 摘要，合并进最近段首条真实 user（避免连续 user）；可再折叠 ≤2 层；
- 顺序原因：先做不花钱的，能省就省；摘要折叠花钱（一次 LLM 调用），留给真正需要时。自动触发（生成前占用 ≥ compact_threshold，默认 0.9）+ 手动 `/compact` 任意时刻 + 连续 3 次失败熔断（自动停用、手动仍可用）。

## F3. 压缩为什么不引本地 tokenizer？
**考察点**：工程取舍（spec N1）。
**参考答案**：占用判断全以 **API 返回的 usage** 为准，不引 tiktoken/tokenizers——少一个依赖、不用维护分词版本差异；代价是"压缩前不知道精确能省多少"，所以压缩后 `lastInputTokens` 重置为 0，**由下一次请求的 usage 复核效果**。这是"以观测代替估算"的取舍，面试可展开。

## F4. prompt 缓存怎么用？cache_control 断点打在哪？命中怎么统计？
**考察点**：降本提效 + 客户端/服务端分工。
**参考答案**：
- 分工：**缓存断点是客户端打的**（我们请求里 `cache_control:{type:ephemeral}`，打在 system 和每个工具定义上，prefix 稳定天然命中）；**命中统计是服务端回传的**（Anthropic `cache_read/creation_input_tokens`、OpenAI `cached_tokens`、DeepSeek `prompt_cache_hit_tokens`），我们解析进 `StreamEnd` 并在完成行展示。
- DeepSeek `/anthropic` 端点实测：需要显式 cache_control + 足够长前缀才命中（短 prompt 两轮 cache=0）。provider 有 `prompt_cache: false` 开关，兼容不识别 cache_control 的端点。
- 面试可补一句业务价值：长会话每轮省大部分输入 token 的钱和首 token 延迟。

## F5. 会话存储为什么改 JSONL？迁移/容错怎么做的？
**考察点**：存储设计。
**参考答案**：之前每轮整文件原子写 O(n)；改 JSONL 追加写 O(1)——每次 save 追加一条 **last-wins 的 meta 行** + 自内存 cursor 起的新消息行；加载取最后一条 meta。配套：旧 `.json` 自动迁移（首次 save 转 .jsonl 并删旧文件）、损坏行跳过并警告、历史收缩（如回滚后消息变少）整文件重写、列表按 id 去重（迁移崩溃窗口可能并存）、tool_result 单条 64KB 截断、不含 api_key。

## F6. Ctrl+C 中断经历了哪些坑？
**考察点**：真机发现问题 + 系统级调试能力。
**参考答案**（这个要能讲成小故事）：
1. **DumbTerminal 信号不注册**：受限 PTY 下 JLine `Terminal.handle` 只存 handler 不注册信号 → Ctrl+C 直接杀进程 → 改 JVM 级 `Signals.register("INT", …)`（真机复测通过）；
2. **弱内存模型可见性**（Apple Silicon）：信号线程写 / 主线程读无同步 → 逃生门/取消失效 → 跨线程字段加 volatile、`exitRequested` 改 AtomicBoolean；
3. **逃生门粘性**：跨 runTurn 不清零，避免被压缩/计划循环的后续 beginTurn 吞掉；
4. 行为设计：单次 Ctrl+C 只中断本轮（半成品回滚、写 assistant「（已中断）」、不追加悬空 tool_use）；1.5s 内再按一次 = 逃生门，恢复默认 SIGINT 优雅退出（对齐 Codex「再按一次退出」）。

## F7. "会话交替纪律"（spec N3）是什么？为什么重要？
**考察点**：对协议约束的理解。
**参考答案**：user/assistant 必须交替、无悬空 tool_use、无连续同角色消息——因为 Anthropic 严格端点/代理对连续 user 会直接 `400 roles must alternate`（真机排查过 /rewind 产生的连续 user 已记 M8+ 待修）。所以：中断标记用 **assistant 角色「（已中断）」**（不是 user，否则紧接着提问就连续 user）；压缩摘要合并进首条真实 user；中断不追加进行中那轮的 tool_use/tool_result。这是所有"往会话里加东西"的功能的公共约束。

# G. 并发 / 扩展 / 系统设计

## G1. 当前并发模型？为什么这样设计？
**考察点**：对现状的清醒认识。
**参考答案**：单对话串行——每轮新建 LlmClient 实例 + UI 主线程消费；`LlmStream` 每流一个后台线程（事件生产）+ 队列（消费）。规避了客户端实例字段并发写（M1 的务实选择）。**明确知道这是 M5 要改的**：`AnthropicClient/OpenAiClient` 的流累积状态（inputTokens/thinkingAccum 等）是实例字段，同一实例并发 `stream()` 有数据竞争，M5 先重构为 **per-call 状态持有者**。

## G2. 如果要支持并行工具执行和 Subagents，你怎么设计？
**考察点**：系统设计（很可能被追问"你项目下一步"）。
**参考答案**：
- ① 并发安全重构：客户端累积状态从实例字段挪到 per-call 状态对象（`LlmStream` 已是现成锚点：每流一个队列+cancel/join）——**硬前置**，先做这个再做并行；
- ② 并行工具执行：`ToolExecutor` 接口不变，新增 `ParallelToolExecutor`——读类并行（read/grep/glob）/ 写类串行（write/edit/bash 顺序）、**结果按原调用顺序回填**（Anthropic 一次性回填的协议约束）；
- ③ Subagents/Task：父 agent 派生子任务 = 独立 Conversation + 独立权限上下文 + 独立护栏上限，子任务结束后把**结果摘要**回填父上下文（不是整个子历史）；子任务结果回填同样守 N3 交替纪律与双协议兼容。
- 面试加分：主动说出"并行后跨线程可见性是重灾区（参考 M4 中断加固的教训）"。

## G3. 如果要接 MCP（Model Context Protocol），怎么设计？
**考察点**：扩展性 + 协议理解（M6 规划）。
**参考答案**：MCP server 是 stdio JSON-RPC 子进程——做一个轻量客户端（启动子进程 + 行协议收发 + 工具列表发现），把远端工具注册进现有 `Tool` 抽象（name/description/inputSchema），让 `ToolRegistry` 和权限系统无感。收益：协议层（LLM 对话）零改动，工具层扩展；权限/安全照旧套在统一 Tool 抽象上。面试可提"这验证了 Tool 抽象的价值"。

## G4. 怎么保证两个 provider 行为一致？测试怎么 mock？
**考察点**：可测试性。
**参考答案**：`MockHttpServer`（本机 HTTP server）+ 脚本化 SSE（按请求返回预先写好的事件流）——真实 LlmClient 打 mock server，端到端跑真实工具循环；双协议各写一套脚本（anthropic tool_use ↔ openai function_call）断言收敛后的事件/回填一致。215 个测试里大量是这类集成测试，不依赖真实密钥，CI 可跑。

## G5. 长会话最怕什么？你的系统怎么兜底？
**考察点**：把多个模块串成"稳定性"故事。
**参考答案**：怕四件事——上下文溢出（告警 + 自动压缩）、成本失控（prompt 缓存 + 压缩省 token）、单轮卡死（60 步上限 + 120s 空闲超时 + Ctrl+C 中断 + 逃生门）、崩溃丢数据（JSONL 追加写 + meta last-wins + 损坏容错）。面试就把这四条作为"稳定性"的骨架讲。

# H. 反思与反问

## H1. 你觉得自己项目最大的不足？
**考察点**：诚实 + 改进方向（别只说"没有"）。
**参考答案**：挑 2-3 个真实边界——① 无 OS 级沙箱（应用层守卫，M7）；② 并行/Subagents 未做（M5，客户端并发安全是硬前置）；③ 无结构化输出校验（工具参数靠模型自觉 + 错误回填自愈，M8+）；④ /rewind 回滚记录会产生连续 user 消息（已知边界，M8+ 修）。每个都要能接"为什么没做 + 什么时候做 + 怎么做"。
